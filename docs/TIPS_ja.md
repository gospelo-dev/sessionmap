# Tips

実際のマシンで sessionmap を使って得られた知見です。いずれも再現可能な実測値に基づいています。

[English](https://github.com/gospelo-dev/sessionmap/blob/main/docs/TIPS.md)

## OpenCode は「サーバー1つ + attach 複数」で動かす

`opencode` を普通に起動するとセッションごとに1プロセスが立ち、**それぞれが起動コストを丸ごと払います**。`opencode serve` 1つに `opencode attach` をぶら下げる構成にすると、そのコストを1回だけで済ませられます。

**ただし得になるのは2本目からです。** 1本だけなら約 190 MB 損をします。

### 実測値

macOS 26.6.2 / opencode 1.18.29、`footprint -p` による物理フットプリント。

| セッション数 | `opencode` × N | `serve` + `attach` × N | 差 |
|---:|---:|---:|---:|
| 1 | 606 MB | 798 MB | +192 MB |
| **2** | 1,212 MB | **985 MB** | **−227 MB** |
| **3** | 1,818 MB | **1,131 MB** | **−687 MB(38%)** |
| 4 | 2,424 MB | 約 1,390 MB | 約 −1,030 MB |

1〜3 の行は直接測定した値、4 の行は下記モデルからの予測です。なお**比較したセッションは両構成とも軽いもの**(コンテキスト 16k 程度)なので、これは「N セッションを開いている状態のコスト」の公平な比較です。実際の作業を抱えれば**どちらの構成も増えます** — 「引き換えに失うもの」のクライアント側の数字を参照してください。

**サーバーはクライアント数に比例して増えません:**

```
0本   244 MB
1本   575 MB   +331 MB  ← 一度きりの初期化であって、セッションごとのコストではない
2本   553 MB
3本   493 MB            ← 増えない
```

この最初の跳ね上がりこそが「1本だけだと損」の原因であり、同時に「2本目で一気に逆転する」理由でもあります。なおサーバーの数値はヒープが回収されるたびに 490〜590 MB のあいだで揺れるので、固定値ではなく幅として捉えてください。

attach クライアント1本あたり約 213 MB なので:

```
opencode × N        ≈ 606 N
serve + attach × N  ≈ 540 + 213 N        (N ≥ 1)

逆転条件:  540 + 213 N < 606 N  →  N ≥ 2
```

単独 TUI が高価なのは、**ターミナルに加えてエージェント本体を丸ごと内包している**からです(606 MB に対し、素のサーバーは 244 MB)。ただし分離すればこの数字が綺麗に割れるわけではありません — 素のサーバー 244 MB + クライアント 213 MB = 457 MB で、606 MB にはなりません。重要なのは**形**の方で、**ターミナルはセッションごとに払い、エージェント本体は1回だけ払う**という構造になります。

クライアントが「ビュー」であるのは、**セッションの状態を所有していない**という意味です。DB に自分の行を持たず、サーバーを強制終了させたときも新しいサーバーに接続し直して作業を継続しました。ただし**薄い端末ではありません**。213 MB は独立した1つのランタイムで、画面描画とスクロールバックを自前で抱えています。

### 使い方

```sh
opencode serve                          # 1回だけ。127.0.0.1:4096 で待受
opencode attach http://127.0.0.1:4096   # 各プロジェクトで、必要なだけ
```

sessionmap ではサーバーがセッション行、クライアントはビューとして並びます:

```
● opencode  56753   553M   30m12s   2h26m!   16k  serve   リファクタリング作業中
● opencode  58111   223M   28m46s      -      -   attach  (view of 127.0.0.1:4096 — session runs in pid 56753)
● opencode  88167   208M    3m39s      -      -   attach  (view of 127.0.0.1:4096 — session runs in pid 56753)
```

### 引き換えに失うもの

- **サーバーへの `x` は全セッションのメモリを一度に落とします。** メモリが全か無かになり、**終わった1つだけを解放して他を動かし続ける、ができません**。単独プロセス構成ならそれができます
- **クライアント1本 213 MB は「床」であって「固定費」ではありません。** これは何も開いていないときの値です。実際のセッションを開けば、**表示のために会話履歴を抱えます**:

  | セッションのコンテキスト | クライアント |
  |---:|---:|
  | なし(素のクライアント) | 213〜267 MB |
  | 16k | 237 MB |
  | 62k | 346 MB |

  測定は2点のみ、いずれも起動直後の値なので、傾きは目安として扱ってください。サーバー側は対応する増加を示しませんでしたが、**サーバー自体が ±50 MB 揺れる**ため、「サーバーは何も持っていない」ことの証明にはなりません。**クライアントは表示している作業量に応じて膨らむ**と見積もってください

セッションの状態そのものは永続的で、これは良し悪しの両面があります。サーバーを強制終了させても失われるものはありませんでした — 接続していたクライアントは自力で新しいサーバーに再接続して作業を継続しました。セッションは SQLite に存在し、サーバーがそれを読み直すためです。便利ではありますが、**離席しても何も自動的に整理されない**ということでもあります。(実行中のターンがビューの喪失を越えて継続するかは未検証です)

## 長い会話は「持っている」ことではなく「開いている」ことが高い

OpenCode のクライアントを重くするのは、**抱えているコンテキストの大きさではなく、表示している履歴の件数**です。この2つは別物で、メモリを予測できるのは前者だけです:

| セッション | 保存済み履歴 | コンテキスト | クライアント |
|---|---:|---:|---:|
| A | 14 parts | 16k | 245 MB |
| B | 33 parts | 51k | 259 MB |
| C | **5,237 parts** | 62k | **351 MB** |

B は A の3倍のコンテキストを持っていますが、差は 14 MB。C は B とほぼ同じコンテキストで**履歴が159倍**、差は 92 MB です。

その大半は **replay バッファ** — スクロールして遡れるように画面へ描き戻された履歴です。セッション C を3通りで開くと:

| | クライアント | ピーク |
|---|---:|---:|
| `--mini`(replay あり) | 390 MB | 611 MB |
| `--mini --replay-limit 50` | 329 MB | 386 MB |
| `--mini --no-replay` | 280 MB | 334 MB |

replay を切るだけで **110 MB**、ピークでは **277 MB** 減ります。素のクライアント(約 245 MB)と比べると、**長いセッションのコストの4分の3は画面上の履歴**ということになります。

**そして通常の TUI には、これを制限する手段がありません。**

```
$ opencode attach ... --replay-limit 50
Error: --replay-limit requires --mini
```

節約するにはインターフェースごと切り替えるしかありません。それが変わるまでの実務的な指針は単純です — **読んでいないビューに、長い過去セッションを開いたままにしない。** 履歴はどちらにせよ DB に安全に残っています。**払っているのは、それを画面に載せておくための費用です。**

(測定は `--mini` 内での比較なので、確定しているのは相対的な効果です。通常 TUI で何 MB 減るかは不明。1セッション、各1回の測定)

## メモリ順ではなく放置時間順に並べる

TUI では `i`、スクリプトなら `--json | jq 'sort_by(.idle_secs)'`。

メモリは「どのセッションが大きいか」を教えてくれますが、放置時間は「どれが終わっているか」を教えてくれます。**いま使っている 600 MB のセッションは問題ではありません。9時間前に触ったきりの 400 MB のセッションが問題です。** 放置時間で並べれば、本当に忘れているものが上に来ます。そしてそれらは、数字の全額が回収可能です。

## 数字を自分で確かめる

```sh
footprint -p <pid> | grep phys_footprint      # macOS で sessionmap が表示している値
vmmap --summary <pid> | grep "WebKit Malloc"  # そのうち JS ヒープはどれだけか
leaks <pid> | tail -2                          # ネイティブなリーク(たいてい ほぼ 0)
```

`ps` の RSS は比較に使えません。カーネルが圧縮したページが見えなくなる一方、フットプリントが除外する共有実行ページを数えてしまうためです。同じマシンで、放置されたセッションは **RSS 218 MB に対しフットプリント 1.4 GB**、起動直後のセッションは **RSS 918 MB に対しフットプリント 606 MB** でした。**両方向に外れます。**
